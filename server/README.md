# Кандидат серверного создания личного чата (v2)

> **Не деплоить в текущий Firebase-проект.** Этот код не подключён к клиенту, не описан в production `firebase.json` и не запускает миграцию. Перед внедрением необходимы аудит действующих rules, блокировки/настройки приватности, сохранение всех старых диалогов и проверка реального проекта.

## Протокол

1. Клиент вызывает `createPrivateChatV2({ partnerId })` с Firebase Auth.
2. Сервер берёт отправителя **только из `request.auth.uid`**, а не из параметров запроса.
3. Проверяет существование получателя Firebase Auth.
4. Строит стабильный неколлидирующий `chatPairs/{hash}` через `conversationPairKey`.
5. В транзакции повторно использует активный диалог либо атомарно создаёт `chats/{randomId}` и `chatPairs/{hash}`. При параллельных запросах транзакция повторяется и не создаёт два активных чата.
6. В `chats/{randomId}` лежат `participants`, `state: active`, `version: 2` и серверное время создания.

## Блокировки в серверном протоколе

Для **будущей** реализации блокировок используется схема `users/{uid}/blockedUsers/{otherUid}`: наличие документа означает, что владелец запретил контакт. Оба callable endpoint читают оба направления **внутри Firestore-транзакции** и отказывают в создании/отправке, если блокировка есть хотя бы у одного участника. Изменение документов блокировки конфликтует с транзакциями, которые их читали, и вызывает повторную проверку. Отсутствие/ошибка чтения снимка не трактуются как разрешение.

**Важно:** интерфейса управления этим списком, авторизованных правил записи/чтения и миграции старых блокировок ещё нет; этот код пока не подключён. Перед запуском нужно разрешить каждому пользователю управлять **только своим** списком блокировок в production Security Rules и проверить их на эмуляторе. Администраторский SDK на сервере обходит клиентские правила, поэтому их отсутствие нельзя компенсировать проверкой только на клиенте.

## Отправка сообщений v2

`sendPrivateMessageV2({ chatId, text, clientMessageId })` проверяет авторизацию, текст (1–2000 символов), `version: 2`, статус `active` и членство в `participants`. Транзакция создаёт сообщение и обновляет превью обоих участников; счётчик непрочитанных получателя увеличивается, у отправителя сохраняется. При серверном переводе чата в `deleting` транзакция конфликтует с параллельными отправками и повторно проверяет статус.

Клиент создаёт новый UUID v4 в момент отправки сообщения и **повторно использует тот же `clientMessageId` при сетевом повторе**. Сервер выводит детерминированный идентификатор документа из `chatId`, `request.auth.uid` и UUID с разделением по длинам полей. Транзакция проверяет, не было ли сообщение уже создано: для точного повтора возвращает исходный `messageId` без дополнительных записей и без повторного увеличения `unread`. Повторное использование ключа с другим текстом запрещено. При новой отправке (даже одинакового текста) нужен новый UUID.

Это **не полноценная система доставки**: ещё нужны ограничение частоты, полный жизненный цикл блокировок, серверные read receipts и тесты с конкурентными запросами, включая реальные Firestore-транзакции. Клиент пока не подключён к endpoint; UUID-ключ является частью будущего протокола.

## До реального запуска

- Экспортировать существующие Firestore Security Rules и проверить все коллекции.
- Завершить UI/правила доступа/миграцию блокировок и отдельно проверить настройки приватности профилей.
- Создать миграцию legacy `chats/{UID_UID}/messages` с резервной копией, индексом соответствий и проверкой коллизий.
- Установить и протестировать доступ к новым сообщениям только для подтверждённых участников.
- Отдельно перенести запись списков чатов и счётчиков непрочитанных на сервер.
- Добавить серверное удаление с состояниями `active → deleting → deleted` и запретом новых отправок.
- Добавить App Check, ограничения частоты, мониторинг и сценарии отказов.
- Переключить клиент на endpoint только после прохождения интеграционных тестов.

`npm test` в корне проверяет чистые функции индексирования пар, нормализации сообщений и политики блокировок. Изолированные тесты правил находятся в `tests/firebase-emulator`; **они не тестируют этот callable endpoint**.
