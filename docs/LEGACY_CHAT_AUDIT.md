# Предварительный аудит legacy-чатов DreamAndGo

> **Только чтение локального JSON. Никаких подключений к Firebase, миграций и изменений данных.**
> Не коммитьте реальные UID, списки чатов или другие выгрузки пользователей в публичный репозиторий.

## Почему необходим аудит

Старый идентификатор собирался как `[uidA, uidB].sort().join('_')`. Он **не доказывает членство** в переписке, а два разных набора UID могут дать одну строку. Поэтому автоматическая миграция только по имени документа опасна.

## Формат входных метаданных

Вручную подготовленный JSON (не содержащий текстов сообщений), например:

```json
{
  "chatIndexes": [
    { "ownerUid": "alice", "partnerUid": "bob" },
    { "ownerUid": "bob", "partnerUid": "alice" }
  ],
  "legacyChats": [
    { "id": "alice_bob", "messageCount": 2, "senderIds": ["alice", "bob"] }
  ]
}
```

- `chatIndexes` — сведения об индексах `users/{ownerUid}/chats/{partnerUid}` с обеих сторон. Не выводите их из `chatId` автоматически.
- `legacyChats` — реально найденные источники `chats/{chatId}` вместе с инвентаризацией вложенных сообщений. `messageCount` и `senderIds` необязательны, но настоятельно рекомендуются.
- `chatId` в записи индекса можно указать, если он был явно сохранён; если поле есть, значение должно соответствовать исходной legacy-схеме.
- Список должен учитывать **все** чаты, в том числе документы с подколлекциями и удалённым родительским документом. Неполный экспорт не является подтверждением безопасности.

Запуск локально:

```bash
npm run audit:legacy-chat -- /absolute/path/to/metadata.json
```

Отчёт печатается в стандартный вывод, никакие файлы не перезаписываются. Код завершения:
- `0` — нет обнаруженных проблем в предоставленных данных;
- `1` — есть записи, требующие проверки;
- `2` — некорректный ввод или ошибка чтения.

## Как интерпретировать отчёт

- `safePairs` — **кандидаты на дальнейшую проверку**, у которых подтверждены оба индекса, найден источник, нет коллизии, известных противоречий отправителей или дубликатов. Это **не разрешение на автоматический перенос**.
- `needsReview` — неоднозначная/неполная пара. Требует изучения и подтверждения реальных владельцев вне имени документа.
- `unreferencedChatIds` — найденный источник без подтверждённых индексов. Нельзя удалять его как «мусор».
- `issues` — дубликаты, повреждённые поля, несовпадения идентификаторов и другие сигналы риска.

Аудит **не проверяет** действующие Firestore Rules, полноту экспорта, правдивость содержимого полей `senderIds`, времена сообщений или backup. Перед переносом необходимы резервная копия, сверка полного количества и хэшей сообщений, повторяемый dry-run, таблица сопоставления старых/новых ID, управляемое переключение клиента и план отката.

## Следующий шаг: dry-run без записи

Для **того же локального JSON**:

```bash
npm run plan:legacy-chat -- /absolute/path/to/metadata.json
```

План содержит:
- `inputFingerprint` (SHA-256 от входного JSON), чтобы отличать версии экспорта;
- `candidates` — исходные идентификаторы, подтверждённые пары, ожидаемое количество сообщений и будущий `targetPairKey`;
- `held` — пары с неустранёнными вопросами, включая отсутствие `messageCount` или `senderIds`;
- `globalBlockers` — обязательные проверки и этапы, которых пока нет.

Поля `targetChatId` намеренно равны `null`: **новый ID не должен угадываться из legacy-пути**. Любой результат имеет `executable: false` — это план проверки, а не операция переноса.

Коды выхода: `0` при отсутствии обнаруженных локальных блокеров (план всё равно не исполняется), `1` при неоднозначных парах/проблемах аудита, `2` при ошибке ввода.

Для реального переноса дополнительно потребуются проверенный полный экспорт, резервная копия и тест восстановления, сверка хэшей **каждого** сообщения, временная остановка legacy-записей, контролируемые серверные транзакции, двойная проверка результата, план отката и подтверждение production rules. Ни один из этих шагов инструмент не объявляет выполненным.

## Проверка целостности сообщений после тестового копирования

Для сравнения двух **локальных** экспортов исходной и целевой истории используйте:

```bash
npm run verify:chat-copy -- /absolute/path/to/source.json /absolute/path/to/target.json
```

Каждый JSON содержит массив сообщений. Например:

```json
{
  "messages": [
    {
      "id": "message-1",
      "data": {
        "senderId": "alice",
        "text": "Привет",
        "createdAt": { "seconds": 1710000000, "nanoseconds": 0 },
        "read": false,
        "edited": false
      }
    }
  ]
}
```

Экспорт должен включать **все** поля сообщения и сохранять типы полей в одинаковом JSON-формате для источника и цели. В текущей версии ID сообщений также должны сохраняться без изменений. Никакой нормализации текста или исключения «неважных» полей нет: расхождение любого поля считается изменением.

Результат:
- `equal: true` — экспортированные массивы совпали по полным данным и ID;
- `missing`, `extra`, `changed` — отсутствующие, лишние или изменённые ID;
- `sourceIssues` и `targetIssues` — повреждённые записи, включая дублирующиеся ID;
- `sourceDigest` и `targetDigest` — SHA-256 от отсортированных контрольных сумм записей.

Порядок записей в файле и порядок ключей JSON не влияют на результат. Фактическая хронология сообщений должна проверяться отдельно через `createdAt` и согласованный алгоритм сортировки в клиенте.

**Конфиденциальность:** эти два файла содержат реальные личные сообщения. Храните их только в защищённом месте, никогда не прикладывайте к публичным PR/issue и удаляйте по вашей политике хранения. Контрольные суммы не являются шифрованием и не скрывают содержимое от перебора распространённых коротких сообщений, если доступны соответствующие хэши.

Команда ничего не копирует, не подключается к Firebase и не изменяет входные файлы. Код выхода `0` — совпадение, `1` — расхождение, `2` — ошибка входных данных. Даже полное совпадение двух экспортов не доказывает полноту резервной копии или корректность доступа пользователей.

## Журнал прогресса: только репетиция

Модуль `server/migration-journal.js` предоставляет три чистые функции:

- `createMigrationJournal(plan, sourceChatId)` — создаёт журнал для одной проверенной пары из dry-run.
- `recordCopyCheckpoint(journal, { plan, sourceChatId, copiedCount })` — записывает очередной контрольный счётчик, не допуская уменьшения или превышения ожидаемого числа сообщений.
- `verifyCopyCheckpoint(journal, sourceMessages, targetMessages, plan)` — после полной репетиции проверяет поштучные SHA-256 и число сообщений, затем помечает локальную репетицию как `rehearsal_verified`.

Смена `inputFingerprint`, параметров пары или ожидаемого числа сообщений делает прежний журнал непригодным для продолжения. Все операции работают только с переданными объектами в памяти: **не читают и не записывают Firebase, не включают миграцию в продакшене**.

Важно: счётчик `copiedCount` — это контрольная отметка, предоставляемая вызывающей стороной, а не доказательство записи в Firestore. Статус `rehearsal_verified` также **не означает готовность к переключению пользователей**: всё ещё нужны независимая резервная копия и проверка восстановления, актуальные Firestore Rules, проверка реального сервера, окно отката и согласованная остановка старых записей. Журнал хранит только идентификатор исходного чата и хэши — не текст переписки.

## Изолированная репетиция в Firebase Emulator

В CI запускается `server/migration-rehearsal.emulator.test.mjs` на демонстрационном проекте `demo-dreamandgo-chat-rules`. Тесты создают только искусственные сообщения внутри `migrationRehearsals/{runId}`; реальная история `chats/*` не читается и не изменяется.

Репетиция проверяет:
- остановку после одного сообщения и повторный запуск без создания дублей;
- целостность всех полей сообщения и SHA-256 после копирования;
- отказ от перезаписи изменённого сообщения;
- отказ от продолжения при неожиданном документе в целевой коллекции;
- обязательное наличие `FIRESTORE_EMULATOR_HOST`, демо-project ID и безопасного `runId`.

Модуль `server/migration-rehearsal.js` намеренно **не является production-мигратором**. Он не переключает клиентов, не удаляет старую историю и не исправляет конфликт автоматически. Результат `rehearsal_verified` относится только к тестовым данным.

## Репетиция восстановления тестовой истории

Дополнительный CI-тест `server/backup-restore-rehearsal.emulator.test.mjs` восстанавливает искусственные сообщения из снимка исходной коллекции в отдельную `migrationRehearsals/{runId}/restoredMessages`. Он сверяет все поля и SHA-256, проверяет повторное восстановление, частично восстановленную историю и конфликт изменённых данных. Неизвестные и изменённые целевые документы не удаляются и не перезаписываются.

**Ограничение:** снимок существует только в памяти теста. Это проверка алгоритма восстановления, **не** создание долговечной резервной копии, не тест disaster recovery и не подтверждение готовности к production. Для настоящих пользователей всё ещё необходим независимый резервный экспорт, безопасное хранение, регулярные тесты восстановления и разрешение на миграцию.

## Предварительная оценка готовности переключения

Модуль `server/cutover-readiness.js` формирует **неисполняемый** отчёт `assessChatCutoverReadiness` для конкретного `inputFingerprint` из dry-run. Проверяет семь внешних свидетельств: аудит production rules, независимая резервная копия, проверка восстановления, полная сверка истории, остановка старых записей, сценарий отката и разрешение оператора.

Каждое свидетельство должно быть привязано к тому же fingerprint, явно относиться к `production`, иметь ссылку на запись проверки, дату наблюдения и срок действия. Свидетельства из эмулятора, просроченные, непроверенные или от другого плана отвергаются. Неоднозначные чаты и пустой план блокируют отчёт.

**Граница доверия:** эти записи передаются извне и не проверяются модулем криптографически. Даже при `reviewReady: true` результат всегда имеет `productionSwitchEnabled: false` и `executable: false`. Это чек-лист для независимого ревью, а не кнопка включения и не подтверждение безопасности без реальных проверок.
