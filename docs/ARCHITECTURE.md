# Dream&Go — архитектура и правила расширения

Статус: архитектурный контракт для v1.0 и последующих версий  
Связанные документы: [PRODUCT_SPEC.md](PRODUCT_SPEC.md), [DELIVERY_PLAN.md](DELIVERY_PLAN.md)

## 1. Главный принцип

Dream&Go развивается как **модульный монолит**: один веб-клиент и единый backend-контур, но с чёткими границами между пользовательскими функциями.

Это осознанный выбор для текущего масштаба. В v1.0 не создаём микросервисы, универсальную plugin-платформу, сложный dependency injection или абстракции «на всякий случай».

Цель — чтобы после выпуска новую функцию можно было добавить отдельным модулем, не переписывая авторизацию, навигацию, коллекции и существующие пользовательские данные.

**Правило:** расширяемость достигается стабильными контрактами и изоляцией, а не реализацией будущих функций заранее.

## 2. Текущее устройство репозитория

Текущая структура — нативные JavaScript ES Modules:

- `js/app.js` — composition root: создание общих сервисов, подключение модулей, жизненный цикл приложения и регистрация маршрутов.
- `js/core/` — общие механизмы: роутер, события, UI-примитивы и безопасная обработка значений.
- `js/modules/<feature>/` — экран и пользовательский сценарий конкретной функции.
- `js/services/` — доступ к Firebase, запросы, сохранение и серверные операции.
- `js/config/` — конфигурация приложения и Firebase.
- `css/` — общие визуальные правила.

Существующие пользовательские данные уже используют путь вида `users/{uid}/<collection>`. Это legacy-контракт. Не переносить данные и не менять пути только ради красоты архитектуры.

Текущая реализация ещё не полностью изолирована: `app.js` содержит прямое подключение модулей, некоторые сервисы смешивают загрузку данных, обработку ошибок и статистику, а EventBus пока минимален. Это фиксируем как технические наблюдения, а не повод для большого переписывания перед релизом.

## 3. Целевые границы ответственности

### Core

Содержит только действительно общие механизмы, которые не знают о конкретной предметной области:

- маршрутизация и lifecycle навигации;
- сессия/контекст текущего пользователя;
- общие UI-состояния и безопасный вывод;
- общая шина событий, если между модулями есть реальная потребность.

Core не должен импортировать модули путешествий, книг, чатов и другие конкретные функции.

### Feature module

Каждый модуль отвечает за один пользовательский сценарий и владеет своим UI:

- отображение loading / empty / error / ready;
- обработчики действий пользователя;
- локальная логика представления;
- вызов сервисов своей области.

Модуль не должен напрямую обращаться к Firestore, менять документы другой области или импортировать внутренние файлы другого feature-модуля.

### Service

Сервис — граница доступа к данным и операциям:

- проверяет и нормализует входные значения;
- использует текущий UID из доверенного контекста, где это применимо;
- выполняет запрос или вызывает доверенную серверную операцию;
- различает пустой результат и ошибку;
- возвращает предсказуемый результат;
- не сообщает об успешном сохранении до подтверждения backend.

UI не должен знать детали Firestore-запросов, имена внутренних коллекций и правила транзакций.

### Server / Firebase

Любая операция, требующая доверия, атомарности, уникальности, квот или доступа к чужому пользователю, должна проверяться на серверной стороне: Firestore Rules и/или Cloud Functions.

Клиентская проверка — только удобство интерфейса, не механизм авторизации.

## 4. Контракт нового модуля

Новая функция после v1.0 добавляется по следующему шаблону:

1. Создать отдельную папку `js/modules/<feature>/`.
2. Создать отдельный сервис `js/services/<feature>.service.js`, если функции нужны данные.
3. Подключить экран к маршрутизатору через composition root. Не добавлять бизнес-логику в `app.js`.
4. Использовать общие UI-примитивы, формы, состояния и дизайн-токены.
5. Не импортировать внутренние реализации соседних модулей. Общий код поднимать в `core` только при наличии минимум двух реальных потребителей.
6. Доступ к данным выполнять только через сервисный слой и разрешённые серверные операции.
7. Определить owner UID, видимость, допустимые поля, ограничения размера и правила удаления.
8. Добавить тесты сервиса, прав доступа и пользовательского сценария.
9. Если меняется схема — сначала описать миграцию, обратную совместимость и rollback.
10. Включать функцию в навигацию только после готовности всего пользовательского сценария.

Новый модуль должен иметь минимально необходимый публичный интерфейс. Внутренние методы и DOM-структура не являются API для других модулей.

## 5. Контракты между модулями

- Предпочитать прямой вызов публичного метода сервиса, если есть один явный владелец операции.
- Использовать EventBus только для событий, на которые действительно подписаны независимые потребители.
- Имена событий — в пространстве имён области, например `dreams:completed` или `chat:message-received`.
- Payload события — небольшой объект с версией контракта при необходимости; не передавать весь Firestore document без причины.
- Событие не заменяет проверку прав и не является источником истины для данных.
- Подписки должны иметь возможность отписки при уничтожении/смене жизненного цикла модуля.
- Не связывать feature-модули через глобальные селекторы DOM, приватные поля или прямой импорт друг друга.

Не внедрять EventBus повсеместно: для простых локальных сценариев обычный вызов проще и надёжнее.

## 6. Совместимость данных и миграции

Существующие документы пользователей считаются legacy API, пока не завершена отдельная миграция.

Для новых полей и типов данных:

- изменения по возможности additive: новые необязательные поля не ломают старого читателя;
- reader терпим к отсутствующим полям и безопасно задаёт defaults;
- новые записи валидируются сервисом и серверными правилами;
- неизвестные поля нельзя автоматически удалять при update;
- не менять значение или тип существующего поля без миграционного плана;
- поле `schemaVersion` добавлять только когда оно реально помогает выбрать формат документа или выполнить миграцию, а не во все документы механически.

Каждая миграция обязана иметь:

1. описание исходной и целевой схемы;
2. dry-run и подсчёт затронутых документов;
3. резервную копию;
4. идемпотентный запуск или устойчивое продолжение после сбоя;
5. отчёт без лишних персональных данных;
6. проверку до/после;
7. rollback или документированную стратегию восстановления;
8. тест на копии legacy-данных и staging.

Сначала совместимый reader, затем writer новой формы, затем миграция, и только после подтверждения — удаление legacy-поддержки.

## 7. Приватность и владение данными

Каждая новая сущность до реализации получает краткую матрицу:

| Вопрос | Обязательное решение |
|---|---|
| Владелец | UID пользователя или явно определённый список участников |
| Видимость | private / public / participants-only |
| Чтение | кто и при каких условиях читает |
| Запись | кто может создавать и изменять |
| Удаление | владелец, участники или серверный процесс |
| Серверная проверка | Rules, Function или оба механизма |
| Индексы и квоты | нужные запросы, лимиты и защита от злоупотребления |

Нельзя делать пользовательский документ публичным по умолчанию. Нельзя использовать скрытие кнопки или проверку UID в браузере как защиту данных.

## 8. Расширения без преждевременного plugin framework

Для v1.0 остаётся статическая регистрация модулей в composition root. Это прозрачно, проверяемо и соответствует масштабу текущего приложения.

После v1.0, когда появится реальная потребность, можно отдельно оценить:

- lazy-loading экранов;
- manifest/registry для маршрутов;
- feature flags для постепенного rollout;
- дополнительные backend capabilities;
- отдельные интерфейсы для новых клиентов.

Ни один из этих механизмов не внедряется только ради гипотетического будущего. Feature flags не должны подменять авторизацию и серверные Rules.

## 9. Архитектурные запреты

- Не превращать `app.js` в место для бизнес-логики новых функций.
- Не давать UI прямой доступ к Firestore.
- Не создавать универсальный CRUD/framework для всех коллекций без доказанной повторяемости.
- Не создавать микросервисы для каждой функции.
- Не добавлять циклические зависимости между модулями.
- Не копировать приватную бизнес-логику одного сервиса в другой.
- Не делать массовый rename/move существующих путей данных без миграции.
- Не сливать post-1.0 возможности в релизную ветку v1.0.
- Не объявлять модуль готовым только по наличию папки и экрана.

## 10. Критерии готовности архитектуры v1.0

Перед выпуском должны быть подтверждены:

- [ ] Core не зависит от feature-модулей.
- [ ] Пользовательские данные доступны через сервисный слой.
- [ ] Смена аккаунта изолирует состояние всех модулей.
- [ ] Ошибка одного feature-модуля не ломает всё приложение.
- [ ] Существующие пути и форматы данных задокументированы.
- [ ] Новые/изменённые схемы имеют правила совместимости и миграции.
- [ ] Firestore Rules и серверные операции проверены в Emulator и staging.
- [ ] Для каждого MUST-сценария есть тесты и понятная точка входа.

Это критерии проверки, а не заявление, что они уже выполнены.

## 11. Чек-лист новой функции после v1.0

Новая идея проходит отдельный Change Request и не попадает в текущий релиз автоматически.

- [ ] Описана пользовательская проблема и ожидаемый результат.
- [ ] Определены границы модуля и публичный интерфейс.
- [ ] Определены владелец данных и правила приватности.
- [ ] Оценено влияние на существующие данные и API.
- [ ] Определены тесты, метрики и rollback.
- [ ] Подтверждено, что функция не требует переписывания ядра.
- [ ] Решение принято владельцем продукта.

**Итог:** v1.0 фиксирует устойчивые границы и качество. Версии 1.x/2.x добавляют возможности отдельными вертикальными модулями, а не бесконечно расширяют базовый релиз.
