# DreamAndGo · Chat v2 — контрольный список выпуска

Статус на 2026-11-15. Кандидат размещён в PR #1, ветка `refactor/security-foundation`.
**Ничего из этого PR не развернуто в production Firebase, клиент legacy остаётся активным.**

## Подтверждено

- Firebase Project ID: `dream-and-go`; Firestore `(default)`, Standard / Native, `eur3` (проверено владельцем через Firebase CLI).
- Серверные кандидаты: создание диалога, идемпотентная отправка, проверка статуса, подтверждение прочтения, счётчик непрочитанных, постраничная история.
- История проверяет Auth, участников, двустороннюю блокировку и состояние `active` до чтения сообщений.
- CI: `npm test` + `npm run check`; отдельные Firestore Emulator tests выполняются на demo-проекте.
- Эмуляторный сценарий `server/chat-history-journey.emulator.test.mjs`: отправка двух участников → страницы истории → прочтение → перезагрузка данных → блокировки.
- Клиент v2 существует отдельно и закрыт feature gate по умолчанию. Текущий gate повторно проверяет rollout и пользователя на каждом действии (при подключённом `getRollout`), включая проверку ответа после ожидания запроса.\n- На коммите `14f77306` три проверки GitHub Actions завершились успешно: `test` (2 запуска) и `chat-rules`. Это подтверждение CI кандидата, **не** проверка production правил.

## Требуется ДО production-деплоя

1. Получить текущие production Firestore Security Rules и проверить все действующие коллекции. Не заменять их кандидатными rules без сверки.
2. Подготовить проверенную резервную копию, карту legacy диалогов и план отката; не запускать миграцию автоматически.
3. Провести аудит прав записи `users/{uid}/blockedUsers` и `privateChatLimits`, внешних пользовательских данных и `chatPairs`.
4. Настроить App Check, квоты, мониторинг ошибок Functions и расходы.
5. Проверить совпадение региона Functions и доступность callable клиента; целевой проект `dream-and-go`.
6. Сделать staging-деплой и провести тест на двух реальных Firebase Auth аккаунтах (отправка, статус, read, восстановление истории, блокировка, повтор запроса).
7. Включить отдельный v2 интерфейс только для allowlist; legacy UI не менять для остальных. При создании сессии передавать актуальный `getRollout` (или при изменении конфигурации пересоздавать сессию), иначе статический `rollout` не сможет отозвать доступ во время сессии.
8. После успешной canary-проверки выполнить сверку истории и счётчиков, проверить rollback и только затем расширять доступ.

## Команды для разработчика

```powershell
npx firebase-tools@latest firestore:databases:list --project dream-and-go
npx firebase-tools@latest firestore:databases:get "(default)" --project dream-and-go
```

Эти команды только читают метаданные. Они **не деплоят** Functions или Security Rules.
