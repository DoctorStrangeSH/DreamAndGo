# DreamAndGo — реестр никнеймов (кандидат, 15.11.2026)

## Статус
Только ветка `refactor/security-foundation`, PR #1. **Не развернуто в production, UI регистрации не переключён.** Существующие приватные документы `users/{uid}` сохраняются без изменений.

Серверный callable `registerProfileV2` требует Firebase Auth и App Check. Email берётся из Firebase Auth, а не из клиентского запроса. Клиент передаёт только никнейм. Функция выполняет одну Firestore-транзакцию:

1. Читает `system/usernameRegistry`, `usernameReservations/{normalized}` и `users/{uid}`.
2. Если реестр не подтверждён как мигрированный, сразу прекращает регистрацию без записи.
3. Если профиль либо никнейм уже существуют, прекращает регистрацию без перезаписи.
4. Атомарно создаёт запись резерва и приватный профиль.

Канонический ключ — ASCII `[a-z0-9_]{3,20}`, регистр игнорируется. Клиент **не должен** создавать, редактировать или удалять документы `usernameReservations` и `system/usernameRegistry`. Они принадлежат только серверу/администратору.

- [ ] Перевести веб-регистрацию с устаревшего `query(users)` / `setDoc(users/{uid})` на callable. Клиент должен объяснять пользователю задержку/ошибку серверной регистрации и корректно восстанавливаться после повторного входа.

**Предупреждение:** единая атомарная транзакция обеспечивает уникальность только после полного backfill существующих никнеймов и отключения старого пути регистрации. Поставить флаг `ready` без этих условий — небезопасно.

## Проверки
`tests/username-reservation.test.js` покрывает закрытый миграционный флаг, отклонение неправильных имён, конфликт регистра, защиту старых профилей и атомарную запись в тестовом адаптере. Для подтверждения конкурентных транзакций нужны интеграционные тесты Firestore Emulator перед rollout.

## Подготовленный скрипт (не запускался на production)

С административными Application Default Credentials и **после резервной копии**:

```bash
node scripts/backfill-username-reservations.mjs --project dream-and-go
```

Режим выше только читает документы, показывает **счётчики без персональных данных**. При `safe:false` или коллизиях скрипт завершает работу с ошибкой.

Только в подтверждённом окне обслуживания, когда старый путь регистрации точно отключён:

```bash
node scripts/backfill-username-reservations.mjs --project dream-and-go --apply --confirm-registration-frozen
```

`--apply` создаёт **только отсутствующие** `usernameReservations` и после этого повторно сверяет пользователей и реестр; не изменяет старые профили и никогда не устанавливает флаг `ready`. Если обнаруживается конфликт, скрипт прекращает работу, оставляя уже созданные корректные резервы на месте для безопасного повторного запуска. Удалять их автоматически нельзя. Для реальной эксплуатации отдельно требуется проверка Firestore Emulator, freeze регистрации, postflight-аудит и явное административное решение по флагу готовности.

## Тестовое подключение клиента (без активации)

`js/services/auth.service.js` содержит альтернативный `signUpWithEmailV2`, который вызывает `registerProfileV2` после Firebase Auth signup. Допуск определяется одновременно `enabled`, `backendReady` и `legacyMigrationVerified`. В `js/app.js` все три значения **явно выключены**; обычная форма по-прежнему использует старый путь, и её переключение требует отдельного решения по rollout.

Нельзя включать `enabled: true`, пока не завершены миграция, QA App Check и доступность callable Functions. При ошибке `already-exists` клиент удаляет только что созданную Auth-запись; при сетевой неопределённости **не удаляет** её (сервер мог успеть сохранить профиль), сообщает пользователю о восстановлении и выходит из сессии. Сценарии проверяются в `tests/signup-v2-flow.test.js` без реальной регистрации.

**Перед выпуском:** добавить серверный путь восстановления Auth-only аккаунта с подтверждённым email/UID, UX для повторного входа после прерванной регистрации, полную проверку в Auth/Firestore Emulator и контроль App Check. Наличие candidate кода не означает готовность для новых пользователей.

## Повторный запрос после потери ответа (идемпотентность)

`registerProfileWithReservedUsername` теперь поддерживает повтор после тайм-аута: если **оба** документа (`users/{uid}` и `usernameReservations/{canonical}`) уже существуют, их владельцы и нормализованные никнеймы совпадают, возвращается `{ ok: true, recovered: true }` **без единой записи**. Функция не изменяет email, профиль, статистику или существующий резерв. Если один документ отсутствует или UID не совпадает, результат — `already-exists` без исправления чужих или частично повреждённых данных.

Это защищает от типичного дублирования после потери ответа, но ещё не означает готовый пользовательский UX восстановления Auth-only профилей. Для него требуется отдельный проверенный сценарий после повторного входа с подтверждением личности, App Check и ограничением частоты запросов. До этого этапа флаг rollout остаётся выключенным.

## Восстановление при повторном входе (кандидат)

Добавлены `getRegistrationStateV2` (Auth + App Check) и методы клиента `getRegistrationStateV2()` / `recoverRegistrationV2(username)`. Read-only статус принимает только UID из Firebase Auth, не позволяет спрашивать чужой профиль и не возвращает email, содержимое профиля или занятые никнеймы:

- `complete`: профиль уже существует — **никаких новых записей**.
- `needs-profile`: Auth существует, профиль отсутствует и реестр миграции подтверждён — можно попросить пользователя ввести свой никнейм и повторить `registerProfileV2`.
- `temporarily-unavailable`: реестр ещё закрыт или не подтверждён — **не создавать профиль**.

При включённом пилотном флаге вход больше не вызывает старый `setDoc({lastLogin}, {merge:true})`, поскольку тот мог создать *пустой* `users/{uid}` и заблокировать восстановление. Для штатных старых аккаунтов при выключенном пилоте логика не меняется.

**Не закончено:** UI восстановления не показывается автоматически; до включения этого потока нужны тесты двух клиентов с Auth/Firestore Emulator, явный экран восстановления и проверка того, как приложение реагирует на вход без профиля. Флаги в `js/app.js` остаются выключенными.
