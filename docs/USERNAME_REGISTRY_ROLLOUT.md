# DreamAndGo — реестр никнеймов (кандидат, 15.11.2026)

## Статус
Только ветка `refactor/security-foundation`, PR #1. **Не развернуто в production, UI регистрации не переключён.** Существующие приватные документы `users/{uid}` сохраняются без изменений.

Серверный callable `registerProfileV2` требует Firebase Auth и App Check. Email берётся из Firebase Auth, а не из клиентского запроса. Клиент передаёт только никнейм. Функция выполняет одну Firestore-транзакцию:

1. Читает `system/usernameRegistry`, `usernameReservations/{normalized}` и `users/{uid}`.
2. Если реестр не подтверждён как мигрированный, сразу прекращает регистрацию без записи.
3. Если профиль либо никнейм уже существуют, прекращает регистрацию без перезаписи.
4. Атомарно создаёт запись резерва и приватный профиль.

Канонический ключ — ASCII `[a-z0-9_]{3,20}`, регистр игнорируется. Клиент **не должен** создавать, редактировать или удалять документы `usernameReservations` и `system/usernameRegistry`. Они принадлежат только серверу/администратору.

## Обязательные действия перед включением

- [ ] Сделать резервную копию реальной Firestore и сверить все старые профили (включая отсутствующие поля никнейма).
- [ ] Проверить коллизии по каноническим именам и ручным способом разрешить конфликты. Нельзя молча удалять или переименовывать аккаунты.
- [ ] Написать и проверить в dry-run отдельный скрипт backfill `usernameReservations` с проверкой сохранности каждого UID; предусмотреть повторы и остановку без потери данных.
- [ ] Убедиться, что в момент backfill регистрация старым способом не может добавлять новых пользователей, иначе реестр будет неполным.
- [ ] Только после независимой сверки количества/UID и полного отсутствия конфликтов **администратор** может установить `system/usernameRegistry = { ready: true, schemaVersion: 1, legacyBackfillComplete: true }`.
- [ ] Проверить сценарии двух новых аккаунтов, одинаковых никнеймов с разным регистром, обрыва соединения, повторных запросов и существующих пользователей в staging на реальном эмуляторе.
- [ ] Перевести веб-регистрацию с устаревшего `query(users)` / `setDoc(users/{uid})` на callable. Клиент должен объяснять пользователю задержку/ошибку серверной регистрации и корректно восстанавливаться после повторного входа.
- [ ] Проверить Firestore Rules: никакого клиентского `create` для `usernameReservations`, запрет записи чужих `users`; не публиковать набор правил до полного аудита зависимых функций.
- [ ] Оценить отдельно жизненный цикл удалённого Firebase Auth аккаунта и очистку резервов: **никнейм автоматически не освобождается**, иначе возможен захват личности.

**Предупреждение:** единая атомарная транзакция обеспечивает уникальность только после полного backfill существующих никнеймов и отключения старого пути регистрации. Поставить флаг `ready` без этих условий — небезопасно.

## Проверки
`tests/username-reservation.test.js` покрывает закрытый миграционный флаг, отклонение неправильных имён, конфликт регистра, защиту старых профилей и атомарную запись в тестовом адаптере. Для подтверждения конкурентных транзакций нужны интеграционные тесты Firestore Emulator перед rollout.
