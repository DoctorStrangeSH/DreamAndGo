# Firebase Security — проверка перед публичным запуском

Этот файл — **аудит архитектуры клиента**, а не доказательство корректности действующих Firestore Security Rules. В репозитории нет актуального файла правил и тестов эмулятора. Не публикуйте Dream&Go для большой аудитории без проверки конфигурации Firebase проекта.

## Особенности существующей схемы

| Путь | Содержимое | Требование к доступу |
| --- | --- | --- |
| `users/{uid}` | Профиль, email, статистика, настройки | Чувствительные поля не должны отдаваться при публичном поиске; для публичного профиля нужна отдельная проекция |
| `users/{uid}/dreams/{dreamId}` | Мечты и признак `isPublic` | Владелец пишет; чужие читают только явно опубликованные мечты |
| `users/{uid}/friends/{friendUid}` | Список друзей | Изменение дружбы требует согласованного серверного протокола |
| `users/{uid}/friendRequests/{uid}` | Входящие запросы | Создание отправителем, чтение/управление получателем по строгим правилам |
| `users/{uid}/sentRequests/{uid}` | Исходящие запросы | Аналогично, две записи должны согласовываться |
| `users/{uid}/chats/{partnerUid}` | Списки диалогов, предпросмотр, unread | Читать только владельцу; сервер проверяет идентификатор партнёра |
| `chats/{chatId}/messages/{messageId}` | Тексты сообщений | Читать только участникам, изменять или удалять своё сообщение по правилам продукта |

## Критические сценарии для тестов эмулятора

1. Неавторизованный клиент не читает ни один приватный профиль, список друзей, чат или сообщение.
2. Пользователь A не может изменить `users/B`, `stats`, достижения и чужие личные записи.
3. Пользователь A не может прочитать закрытую мечту пользователя B, даже зная её ID.
4. Сообщения читаются только участниками диалога; A не может редактировать сообщение B.
5. Проверить создание/принятие заявок в друзья, удаление дружбы и диалогов.
6. Проверить, что выдача поиска не раскрывает email, настройки и другую закрытую информацию.
7. Ограничить размер, типы полей, допустимые значения и частоту чувствительных операций на сервере.
8. Проверить конкурентную регистрацию одного ника и его переименование.

## Архитектурные изменения перед масштабированием

- Разделить `users/{uid}` (приватные данные владельца) и публичный профиль, например `publicProfiles/{uid}`, без email и служебных полей. Firestore Rules контролируют документы, а не отдельные поля возвращаемого документа.
- Индекс никнеймов резервировать атомарно на сервере: `usernames/{normalizedName}` → `uid`. Клиентские `query` не гарантируют уникальность при гонке регистраций.
- Мигрировать старые профили с резервной копией и предварительным поиском коллизий без учёта регистра.
- Определить политику удаления сообщений: «удалить у себя» отдельно от «удалить для всех», с проверкой участия в чате и прав отправителя.
- В интерфейсе не обещать сквозное шифрование: Firebase Auth/Firestore сами по себе не создают E2EE.

## Как проводить проверку

1. Получить и сохранить действующие правила Firebase через авторизованный административный канал.
2. Скопировать их в репозиторий с конфигурацией эмулятора и автоматическими `@firebase/rules-unit-testing` тестами.
3. Запустить тесты с несколькими пользователями, включая гостя и атакующего.
4. Только после зелёных тестов и ревью согласовывать изменения правил на реальном проекте.
5. Повторить полный регрессионный тест приложения до включения публичной индексации.

**Важно:** этот документ не изменяет правила в Firebase Console и не даёт разрешения на открытие текущей базы.
