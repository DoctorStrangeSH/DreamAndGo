# DreamAndGo — план безопасного восстановления Firestore (15.11.2026)

**Состояние:** протокол для review, не production deployment. По сообщению владельца в Firebase Console опубликовано аварийное правило `allow read, write: if false`; это не проверено административным API. App Check для Dream&Go Web зарегистрирован (скриншот владельца), а инициализация Enterprise-провайдера пока только в PR #1.

## Обнаруженные несовместимости старого клиента

| Место | Запрос или запись | Почему нельзя просто разрешить всё авторизованным |
| --- | --- | --- |
| `auth.service.js` | Поиск уникальности через два `query(users, where(username...))` | Правила на `users` не умеют скрыть email и настройки из документа результата. Даже `allow read: if request.auth != null` раскрывает PII. |
| `friends.service.js`, `chat.service.js`, `realtime.service.js` | `getDoc(users/{чужойUid})`, поиск пользователей | Нужны `publicProfiles` или ограниченные серверные методы, а не чужие приватные документы. |
| `friends.service.js` | Batch пишет `friendRequests` и `sentRequests` в двух разных пользовательских деревьях, принимает заявку записью взаимной дружбы | Наивное правило «владелец своей подколлекции» ломает операции; правило «любой участник пишет» создаёт возможность подделать отношения. |
| `chat.service.js` | Сообщение плюс записи в `users/{sender}/chats` и `users/{receiver}/chats` | Нельзя доверять клиенту чужую запись unread/metadata; кандидат server chat v2 уже изолирован в PR. |
| `dreams`, `books`, `travels`, `movies`, `restaurants` | CRUD `users/{uid}/{category}`, `orderBy(createdAt)`, иногда `where(status/category/cuisine)` | Возможно ограничить владельцем, но нужно валидировать поля на create **и** update; модель частично динамическая. |
| `dailyTasks`, `notifications`, `achievements` | Изменяемые на клиенте награды, счётчики и уведомления | Требуют server-authoritative начисления либо строгих переходов и лимитов; нельзя выдавать привилегии по самозаписанным полям. |

## Сценарий восстановления без утечки существующих профилей

1. **Сохранить аварийный deny-all в production** до подтверждённого снимка схем и пробного прогона. Не возвращать `allow read, write: if true`.
2. Получить административный экспорт структуры Firestore **без публикации PII**: имена коллекций, типы и допустимые поля, особенности старых профилей. Не копировать пользовательские email/сообщения в GitHub issue или чат.
3. Подготовить и проверить в эмуляторе **начальный ограниченный срез**: авторизованный владелец читает `users/{uid}` и свои подколлекции; записи только по явно валидированным схемам. Чужие `users` — deny. Гостевой `list(users)` — deny.
4. Перевести поиск и публичные карточки на `publicProfiles` / проверенные callable Functions. Провести backup, dry-run миграции и проверку коллизий никнеймов. После этого можно запретить клиентские `query(users)`.
5. Обработку дружбы, уведомлений, чатов, наград вынести на авторизованные серверные операции; только затем открывать необходимые записи.
6. Прогнать тесты: два обычных пользователя + гость + попытки подмены UID/роли, чтения PII, записи чужого документа, 1 МБ строки, удаления обязательных полей, изменения createdAt, query mismatch, подделки дружбы и начисления наград.
7. Проверить App Check получение токена на GitHub Pages, **не включать enforcement** для Firestore до обновления клиентов и наблюдения метрик. Server callable с `enforceAppCheck: true` тестировать отдельно.
8. Пробный rollout на staging; review и ручной production deploy только после успешной проверки реальных сценариев с двумя тестовыми аккаунтами.

## Блокер прямо сейчас

В репозитории отсутствует достоверный файл **действующих** production Firestore Rules. Существующий `tests/firebase-emulator/chat.rules` — лишь кандидат для изолированного chat v2. Поэтому нельзя заявлять, что приложение уже восстановлено или безопасно включать широкие разрешения. Сначала нужен подтверждённый снимок реальной схемы и согласованный контракт клиентских записей.

**Инвариант:** Firestore Security Rules защищают документы целиком; `users/{uid}` с email должен быть доступен только владельцу. App Check не заменяет Auth и authorization.
