# DreamAndGo — аудит правил Firestore перед пилотом Chat v2

Дата: 2026-11-15. Проект: `dream-and-go`, база `(default)`, Standard / Native, регион `eur3`.

## КРИТИЧНО: действующие правила получены от владельца\n\nВладелец 2026-11-15 передал правила действующей базы: рекурсивное `match /{document=**}` с `allow read, write: if true`. Эти правила разрешают анонимные чтение, создание, изменение и удаление **любых документов** через клиентский Firestore API. Это не гипотетическая ошибка клиента, а отсутствие контроля доступа на уровне базы. Факт эксплуатации не установлен.\n\nВладелец подтвердил, что **в приложении уже есть реальные пользователи**. Поэтому немедленный `allow read, write: if false` остановит клиентские функции; запрещено тихо развёртывать его или считать простую замену на `request.auth != null` достаточной.\n\n## Что подтверждено в репозитории

- Корневых `firebase.json` и `firestore.rules` нет в ветке `refactor/security-foundation`.
- Есть только `tests/firebase-emulator/firebase.json`, который ссылается на `chat.rules` в той же тестовой папке.
- Тестовый `chat.rules` **не является снимком production rules**. Он намеренно запрещает несвязанные коллекции.
- Тестовые правила допускают клиентские `create/update/delete` для `chats/{chatId}/messages/{messageId}`. Это **несовместимо с моделью v2**, где новые сообщения и статусы прочтения записываются только серверными Functions с проверкой частоты, блокировок, принадлежности и идемпотентности.
- Сервер использует дополнительные документы `chatPairs`, `users/{uid}/privateChatLimits`, `users/{uid}/chats`, `users/{uid}/blockedUsers`.

## Риски, которые нельзя считать закрытыми эмулятором

1. Прямые клиентские записи в v2 сообщения обходили бы серверный антифлуд и детерминированные ID.
2. Нельзя заменить production rules тестовым файлом: остальные разделы приложения потеряют доступ.
3. Пока неизвестны действующие разрешения на изменение блокировок и счётчиков.
4. SDK Admin на сервере обходит правила клиента — успешные серверные тесты **не доказывают** корректность production rules.

## Контрольный план устранения инцидента без необъявленного простоя\n\n1. **Срочно:** владелец фиксирует решение о кратковременном ограничении сервиса либо об ускоренном поэтапном выпуске; риск продолжается до публикации новых правил. По возможности ограничить новые регистрации/доступ, сохранив журнал изменений и снимок правил.\n2. **Зафиксировать состояние:** выполнить проверенную резервную копию Firestore и учесть, что Point-in-Time Recovery в метаданных отключён. Не перезаписывать пользовательские документы массовой миграцией.\n3. **Сначала приватность профилей:** `users/{uid}` содержит `email`, настройки и статистику. Существующий поиск по `usernameNormalized` и получение чужих профилей читает *целые* документы — нельзя просто разрешить общий `read`. Вынести публичные поля в `users_public`, переписать поиск и регистрацию, ограничить чтение `users/{uid}` владельцем.\n4. **Личные коллекции:** `users/{uid}/{dreams|books|movies|travels|restaurants|dailyTasks|notifications}` доступны только владельцу. Требуются валидаторы схем на create/update и неизменяемость идентификаторов; публичные публикации должны жить отдельно.\n5. **Друзья и legacy чат:** существующий клиент записывает также в документы второго участника (`friendRequests`, `friends`, `sentRequests`, `users/{peer}/chats`) и в общую `chats/{chatId}/messages`; для защиты от подделки участников, счётчиков и текста нужны серверные операции либо строго проверяемые атомарные переходы. Чат v2 держать выключенным.\n6. **Тесты до поэтапной публикации:** unauthenticated read/write, чужой профиль/email, чужие коллекции, forged friendships/chats, изменение `role`/счётчиков, oversize поля, право на чтение истории только участникам, реальные запросы поиска и регистрации.\n7. **Развёртывание и мониторинг:** выпускать минимальные согласованные правила с проверкой двух реальных аккаунтов и `permission-denied`; иметь готовый откат на **предыдущие безопасные** правила, но не возвращаться к `allow ... if true`. Проверить журналы подозрительных операций и определить, требуется ли уведомление пользователей по применимым требованиям.\n\n## Следующий безопасный шаг: read-only сверка

Действующие правила уже получены. Нужны подтверждение политики аварийного ограничения сервиса и доступ к безопасному окружению для проверки и публикации. До этого ни безопасный набор правил, ни остановка риска на production не подтверждены.
