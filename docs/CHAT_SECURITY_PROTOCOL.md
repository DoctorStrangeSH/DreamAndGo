# Контракт безопасности личных чатов DreamAndGo (проект, не развёрнут)

> **НЕ ДЕПЛОИТЬ правила по этому документу автоматически.** В репозитории нет экспортированных действующих Firestore Rules; реальный Firebase-проект не проверен. Это технический план и критерии приёмки.

## Обнаруженный блокер

Текущая схема хранит сообщения в `chats/{chatId}/messages`, где `chatId` строится на клиенте из двух UID, разделённых символом `_`. **Отдельного доверенного документа участников нет.** Правило вида «проверить, содержится ли UID в строке chatId» небезопасно: чужой UID можно включить в произвольный ID. Кроме того, использование разделителя без однозначного кодирования UID допускает коллизии.

Списки `users/{uid}/chats/{otherUid}` и поля `unread` сейчас обновляются самим клиентом, в том числе внутри документов второго пользователя. Такие записи требуют отдельного строго ограниченного серверного протокола.

## Целевое устройство

1. Ввести `chats/{chatId}` с `participants` (ровно два UID), `createdAt`, `version`, `state`. Идентификатор сделать независимым от имён/UID (случайный ID Firestore или криптографически однозначная схема).
2. Создавать метаданные чата **только доверенным серверным обработчиком**, проверяющим Firebase Auth и право обоих участников общаться. Клиенту разрешить лишь запрос на создание.
3. Читать сообщения только если `request.auth.uid in resource.parent.participants` через `get(/databases/$(database)/documents/chats/$(chatId))` (конкретный синтаксис правил проверить в эмуляторе).
4. Создавать сообщение только от собственного UID; ограничить длину текста, типы полей и системные даты.
5. Изменение и удаление сообщений разрешать только отправителю, если политика продукта это допускает; запретить изменение `senderId`, `createdAt` и поля участников.
6. Счётчики непрочитанных и предпросмотр последнего сообщения переносить в доверенный серверный обработчик, либо проектировать минимальные строго проверяемые client writes. Не давать произвольно изменять чужие `users/{uid}`.
7. Для удаления всей переписки установить серверный жизненный цикл `active → deleting → deleted`: блокировать новые отправки, выполнять идемпотентные порционные удаления, затем убирать записи участников.

## Миграция без потери истории

Первый подготовительный шаг уже есть: **локальный аудит экспортированных метаданных** [LEGACY_CHAT_AUDIT.md](LEGACY_CHAT_AUDIT.md). Он только помечает безопасные для дальнейшего исследования пары и случаи ручной проверки; не читает и не меняет Firebase и не может подтвердить полноту экспорта. Даже результат без предупреждений не разрешает миграцию без бэкапа и проверки реального окружения.


- Сначала резервная копия и инвентаризация всех `chats/*/messages`, `users/*/chats/*`.
- Выявить неоднозначные/коллидирующие ID и записи без двух согласованных участников. Не угадывать владельцев по строке ID.
- Для каждой подтверждённой пары создать доверенный документ участников или перенести сообщения в новый чат с отдельным ID, сохраняя сопоставление старых ссылок.
- Проверить число сообщений, авторов, время и права в тестовом проекте.
- Подключить клиент к новой схеме под управляемым флагом; только затем включить новые rules.
- Старую схему закрывать после проверки, что все активные диалоги мигрировали и не осталось записей в очереди.

## Негативные тесты эмулятора (обязательные)

| Сценарий | Ожидается |
| --- | --- |
| Гость читает или пишет сообщение | DENY |
| Пользователь C знает ID диалога A—B | DENY чтение, создание, изменение, удаление |
| A отправляет сообщение с `senderId=B` | DENY |
| A изменяет/удаляет сообщение B | DENY |
| A меняет `participants`, `createdAt` или `senderId` | DENY |
| A пишет сообщение слишком большой длины | DENY |
| A редактирует `users/B/chats/A.unread` произвольным значением | DENY |
| A и B одновременно создают чат | Один согласованный диалог без потерь |
| Создание нового сообщения во время удаления | Отклонено после перехода в `deleting` |
| Повторный запуск серверного удаления | Безопасен, без оставшихся сообщений |
| Пользователь меняет UID внутри вычисленного строкового ID | Не даёт чужой доступ |

## Критерий готовности

Нужны: точный экспорт действующих Firestore Rules, тестовый Firebase-проект, Firebase Emulator Suite, правила и тесты под CI, серверный способ создания/удаления и проверенная миграция. До этого **нельзя объявлять систему чатов защищённой** и нельзя деплоить «примерные» правила на продакшен.

## Остановка записей: подтверждение повторных отправок

Кандидатная серверная транзакция различает новую отправку и повтор уже сохранённого сообщения. Если чат переведён из `active` в `frozen`, новые сообщения отклоняются (`failed-precondition`), но точный повтор существующего сообщения с тем же `clientMessageId`, отправителем и текстом подтверждается без дополнительной записи и увеличения непрочитанных. Проверки членства и блокировки остаются обязательными даже для повтора.

В CI Firebase Emulator добавлен тест гонки между записью сообщения и изменением `state` чата. Проверяется атомарный исход: сообщение записано один раз вместе с индикатором непрочитанных **или** транзакция отклонена. Это пока кандидатная реализация v2, не изменение production-клиента и не решение всех вопросов полного переключения legacy-чата.

## Репетиция повторного открытия после отката

`server/chat-rollback-rehearsal.js` в **изолированном Firebase Emulator** повторно открывает только синтетический чат с ID `rollback-drill-*`, версия 2 и состоянием `frozen`. Перед открытием проверяется точное совпадение экспортированных сообщений по ID, всем полям и SHA-256. При изменении или отсутствии сообщения чат остаётся заморожен. Повторное открытие уже активного чата также отклоняется.

Важные ограничения: это тест возвращения **синтетического v2-чата** из `frozen` в `active`, а не откат клиента на legacy-хранилище. Сверка сообщений и изменение состояния теперь выполняются в одной транзакции Firestore: чтение состояния, чтение коллекции сообщений, сравнение и изменение состояния. Это сокращает окно гонки, однако сторонние записи, новые документы-потомки, права доступа и настоящий legacy-откат всё ещё требуют отдельной защиты и тестирования — модуль не предназначен для production. Пользовательские данные не затрагиваются.

## Одновременные запросы на восстановление

Добавлен тест двух параллельных попыток перевода одного синтетического чата `frozen → active`. Обе попытки читают статус в транзакции Firestore; после фиксации первой вторая должна получить отказ, поэтому открытие происходит ровно один раз. История остаётся без изменений. Это проверка конкурентного доступа на тестовом v2-чате, не разрешение на production-откат.

## Сквозная проверка заморозки и восстановления

Тест `server/chat-cutover-journey.emulator.test.mjs` проходит в одной сессии эмулятора весь сценарий кандидата v2: отправка сообщения → заморозка → безопасное подтверждение повторного запроса → отказ в новой отправке → сверка истории → повторное открытие → отправка следующего сообщения. Проверяются количество сообщений и непрочитанных. Второй сценарий изменяет сообщение после заморозки и подтверждает отказ от восстановления.

Это интеграционная проверка **искусственного v2-чата**, а не замена реальной миграции legacy, резервного копирования или проверки production rules.

## Повтор после перезапуска клиента

В кандидатный `ChatOutbox` добавлен метод `restore(chatId, text, clientMessageId)`. Он позволяет новому экземпляру очереди повторно использовать **строго тот же** исходный текст и UUID. Если сервер ранее уже записал сообщение, v2-транзакция распознает повтор и не создаст второе. Изменённый текст для занятого UUID отвергается.

Ограничение конфиденциальности: `ChatOutbox` не сохраняет текст сообщений в `localStorage`, `sessionStorage` или на диск. Восстановление требует, чтобы вызывающая сторона уже имела оригинал сообщения и UUID; после полного закрытия браузера без такого источника нельзя автоматически восстановить намерение. Метод **не подключён к legacy UI** и сам по себе не означает готовой функции восстановления после перезапуска в production.

## Сверка статуса после потери подтверждения

Кандидатная callable-функция `getPrivateMessageStatusV2` принимает `chatId` и исходный `clientMessageId`. Сервер проверяет Firebase Auth, членство в v2-чате, блокировки с обеих сторон и детерминированный ID. Ответ содержит **только** `{status: 'sent', messageId}` или `{status: 'missing'}`; текст переписки не возвращается. Ошибки доступа не подменяются ответом «отсутствует».

`ChatOutbox.reconcile(clientMessageId, lookup)` удаляет ожидающее сообщение **только** после подтверждения `sent`. При `missing` или ошибке соединения исходное намерение остаётся в памяти для осознанного повтора. Параллельные проверки объединяются; проверка не гоняется с отправкой, а завершившийся запрос старой сессии не меняет очередь после выхода из аккаунта.

Важно: `missing` означает только отсутствие записи **на момент чтения**; исходная отправка теоретически ещё может завершиться позже. Повтор обязан использовать **тот же UUID и текст**, а серверная транзакция обеспечивает идемпотентность. Клиент не делает автоматическую повторную отправку по одному результату сверки. Функция пока не развёрнута и не интегрирована с legacy-интерфейсом; эмуляторные тесты проверяют лишь кандидатный протокол.

## Отображение статусов доставки (кандидат v2)

В модуле чата добавлен закрытый набор визуальных состояний `sending`, `checking`, `sent`, `read`, `failed` с русскими подписями для экранных дикторов. Отображение происходит только при явном поле `deliveryStatus` у **исходящего** сообщения. Исторические legacy-сообщения не получают фиктивных галочек; поля `read` и `unread` текущей схемы не считаются доказательством персонального прочтения.

Это **подготовка визуального контракта**, а не уже включённая в production доставка: реализация передачи статусов от `ChatOutbox` в поток UI и надёжных персональных квитанций о прочтении ещё требуется. Проверка тестами подтверждает корректность разметки и отсутствие подстановки произвольного HTML через название статуса.

## Связка очереди с визуальным состоянием v2

`ChatDeliveryController` связывает `ChatOutbox` и отображаемый статус. Создание намерения отмечается `sending`; подтверждённая запись — `sent`; неоднозначный сетевой сбой — `checking`; подтверждённое отсутствие после сверки — `failed` с возможностью **только ручного** идемпотентного повтора. Неизвестный статус не считается подтверждением доставки. Данные остаются исключительно в памяти. На выходе из аккаунта очередь и состояния очищаются, поздние ответы отбрасываются.

`read` допускается только при явном вызове `acknowledgeRead(clientMessageId, serverMessageId)`, где серверный ID точно совпадает с уже подтверждённым отправленным сообщением. В этом этапе **нет** серверного механизма квитанций прочтения и нет подключения контроллера к production UI: вызывающая сторона в будущем обязана проверять подлинность receipt. Тесты покрывают переходы, потерю подтверждения, ошибку сети, выход из аккаунта и недопустимую квитанцию.

## Серверная квитанция прочтения v2

Кандидатная функция `markPrivateMessageReadV2(chatId, messageId)` записывает `read: true` и доверенное `readAt` в транзакции Firestore только для **получателя** сообщения. Проверяются Firebase Auth, ровно два участника v2-диалога, блокировки в обе стороны, реальное существование сообщения, автор-партнёр и совпадение детерминированного ID с исходным `clientMessageId`. Отправитель и посторонний не вправе выставить себе «прочитано». Повторное подтверждение не обновляет временную метку. Замороженные чаты не допускают новых квитанций.

Ограничения: тесты используют только изолированный Firebase Emulator, действующая редакция production Firestore не определялась; работающие rules и legacy UI не менялись. Квитанция означает явный вызов со стороны получателя, но UI ещё должен вызывать её **только после фактического отображения сообщения**, а отправитель — получать подтверждение через защищённый v2-поток. Квитанция теперь в **той же транзакции** уменьшает общий для получателя счётчик `users/{uid}/chats/{partnerId}.unread`, только если он корректен и больше нуля. Повторные и параллельные квитанции одного сообщения не уменьшают счётчик повторно. Просмотр позднего сообщения не затрагивает непросмотренные ранние. Для отсутствующих или исторически некорректных счётчиков нужна отдельная сверка по данным сообщений до production-перехода.

## Подтверждение прочтения на устройстве отправителя

Кандидатный `getPrivateMessageStatusV2` теперь возвращает `read: true/false` **только для исходящего сообщения данного отправителя**, после всех проверок членства и блокировок. Поле отражает доверенную запись получателя, а не предположение о просмотре диалога. `ChatDeliveryController.refreshRead(clientMessageId)` проверяет точное совпадение `messageId`, значения `read === true` и актуальность сессии, после чего меняет `sent → read`. Параллельные проверки одного UUID объединяются. Ошибка сети, отсутствие или несовпадение записи не ставят двойную галочку.

Ограничения: это запрос по инициативе отправителя, **не** realtime-подписка. Отметка получателя пока не вызывается автоматически при реальной видимости сообщения в браузере, а счётчики непрочитанных ещё требуют отдельного протокола. Текущий legacy UI работает как прежде; ни одна кандидатная callable-функция не развёрнута на production.

## Отправка квитанции только после видимости сообщения

Добавлен кандидатный клиентский `ChatReadVisibilityTracker`, использующий `IntersectionObserver`. Он рассматривает только **входящие**, ещё не прочитанные сообщения v2 с валидным серверным ID; сообщение должно быть подключено к DOM, находиться внутри контейнера диалога и иметь не менее 75% пересечения с областью видимости. Дополнительно требуются видимая вкладка браузера (`document.visibilityState === 'visible'`) и активный диалог/сессия (предикат `isActive`). При уходе из диалога `stop()` снимает наблюдение и инвалидирует отложенные операции.

Одновременные запросы для одного ID объединяются, серверный ответ принимается только с тем же `messageId`. Ошибки сети и неподтверждённые ответы не записывают локальный факт прочтения; следующий сигнал видимости разрешает повтор идемпотентной квитанции. Это **эвристика видимости, а не доказательство, что человек прочитал текст**.

Модуль изолирован и покрыт unit-тестами; он пока **не подключён** к legacy DOM и не вызывает production Firebase. При включении v2 вызывающая сторона обязана предоставить авторизованный транспорт `markPrivateMessageReadV2`, передать актуальное состояние диалога и отключать наблюдатель при смене аккаунта.

## Общий курс непрочитанного для нескольких устройств (контракт v2)

Добавлен чистый модуль `server/chat-unread-cursor.js` с контрактом курсора прочтения на пользователя и диалог. Серверная версия должна выдавать каждому сообщению строго возрастающий целочисленный `sequence`; для каждого участника хранится один общий `lastReadSequence`, а не независимый счётчик на устройстве. Непрочитанные вычисляются как входящие сообщения с `sequence > lastReadSequence`. Курсор монотонный: запоздавшее состояние телефона или компьютера не может уменьшить уже достигнутое значение.

Добавлены unit-тесты подсчёта входящих, исключения собственных сообщений, монотонного объединения двух устройств и отклонения некорректных sequence. Теперь кандидатная `sendPrivateMessageTransaction` **атомарно выдаёт** `sequence` и увеличивает серверное `chats/{chatId}.nextSequence` в той же транзакции. Повтор с тем же UUID не меняет sequence; конкурирующие отправители сериализуются через документ диалога. Для прежних v2-диалогов без счётчика начальное значение — 0; некорректный счётчик отклоняется. Это покрыто отдельными emulator-тестами. **Важно:** на исторических сообщениях без `sequence` новый курсор применять нельзя без миграции; функция прочтения хранит индивидуальный `read` и атомарно корректирует материализованный `unread` для новых v2-сообщений, но `lastReadSequence`, историческая сверка `unread` и realtime UI пока не подключены. Следующий шаг — безопасная стратегия перехода и транзакционное продвижение курса с защитой от пропуска непросмотренных сообщений.


## Сверка непрочитанных после офлайна (кандидат v2)

Добавлена защищённая read-only callable `getPrivateChatUnreadV2(chatId)`. Она проверяет Firebase Auth, участие пользователя в v2-диалоге и взаимные блокировки, а затем возвращает только `{ chatId, unread }`. Источник истины — агрегат `count()` по входящим сообщениям `senderId == partnerId` и `read == false`, **не** локальный кеш и не поле предварительного просмотра. Текст сообщений и идентификаторы других пользователей не раскрываются. Это позволяет после длительного офлайна или переустановки сверить число для отображения, не изменяя старые данные.

Для этой составной выборки предусмотрен **только кандидатный** файл `server/firestore.indexes.candidate.json` (поля `senderId` и `read`, область `messages`). Файл не связан с production-конфигурацией и не развёрнут. Перед включением необходимо подтвердить редакцию и параметры production Firestore, применить подходящий индекс и проверить его готовность. Firestore Emulator может не требовать этот индекс, поэтому успех emulator-тестов **не** подтверждает готовность production-запроса.

Ограничения: серверная сверка пока не пересчитывает и не исправляет `users/{uid}/chats/{partnerId}.unread`, а только возвращает точное число для v2-записей с явным `read: false`. Старые legacy-сообщения без этого поля и история до миграции не охватываются. Подписка UI и стратегия синхронизации материального счётчика остаются отдельными шагами. Никаких production-вызовов и деплоя на этом этапе нет.


## Клиентская сверка непрочитанных (кандидат v2)

Добавлен `ChatUnreadController` в `js/core/chat-unread-controller.js`. После явного `refresh(chatId)` он обращается к переданной вызывающей стороной авторизованной функции `getPrivateChatUnreadV2` и публикует результат только при точном совпадении `chatId` и корректном неотрицательном целом `unread`. Состояния: `checking`, `ready`, `unknown`. При сетевой ошибке, неверном ответе или отсутствии подтверждения счётчик становится `null`: интерфейс не должен показывать прежнее число как доказанный результат.

Повторные одновременные проверки одного диалога объединяются; `clear()` при выходе из аккаунта и `remove(chatId)` при удалении диалога отклоняют поздние ответы. Состояния живут исключительно в памяти, без сохранения содержимого сообщений. Unit-тесты проверяют сверку, ошибки, смену аккаунта, конкурентные запросы и несоответствие идентификатора.

**Интеграция ещё не выполнена:** кандидатная модель не привязана к legacy UI, экранным бейджам, подпискам Firestore, автоматическому reconnect или уже развёрнутой Cloud Function. Для тестирования end-to-end понадобится отдельный безопасный rollout v2 и реальный транспорт после утверждения индекса и миграции.


## Автоматическое обновление после офлайна и возврата на вкладку (кандидат v2)

`ChatUnreadRefreshCoordinator` связывает `ChatUnreadController` с событиями `online` и `visibilitychange`. После `start()` он инициирует сверку только для переданного вызывающей стороной набора диалогов, когда вкладка видима и браузер не сообщает `offline`. Совпадающие ID устраняются, ошибочный список целиком отклоняется. Частые повторные события ограничены минимальным интервалом по умолчанию 5 секунд, а параллельные полные проверки объединяются. При `stop()` обработчики снимаются и состояние предыдущего аккаунта очищается, чтобы поздние ответы не попали в новую сессию.

Добавлены unit-тесты включения, ограничения частоты, офлайна/скрытой вкладки, очистки при выходе и ошибочного списка. Это всё ещё кандидатный компонент без подключения к legacy UI: приложение должно само вызвать `start()` после авторизации, предоставить список доступных v2-диалогов и `stop()` при выходе. События возврата/онлайна запускают разовую сверку, **не** realtime-подписку и не периодический опрос.


## Визуальный бейдж непрочитанных (кандидат v2)

Добавлены `getChatUnreadDisplay(state)` и `renderChatUnreadBadge(state)` из `js/core/chat-unread-badge.js`. При подтверждённом `ready` показывается точное число до 99, далее `99+`, а полное значение доступно в русской подписи. Ноль не создаёт бейдж. `checking` и `unknown` показывают отдельные пиктограммы без старого числового значения; повреждённые данные не отображаются. Все строки и CSS-классы формируются из закрытых шаблонов, непроверенные поля пользователя не интерполируются в HTML. Unit-тесты покрывают доступность, переполнение, ошибки и вредоносные значения.

Это **только представление-кандидат**: его ещё нужно включить в реальные компоненты списка чатов и предоставить стили для `chat-unread-badge`. Ни новая разметка, ни transport v2 пока не включены в production UI.


## Привязка бейджей к карточкам диалогов (кандидат v2)

`ChatUnreadBadgePresenter` принимает `resolveSlot(chatId)` и предназначен для обработки `ChatUnreadController.onChange`. Владелец интерфейса предоставляет **отдельный пустой контейнер** внутри каждой карточки диалога — не всю карточку. Компонент меняет содержимое только этого контейнера, не превращает ID в CSS-селектор, очищает прежний контейнер после перерисовки DOM и удаляет бейджи по `onChange(null, chatId)` / `onChange(null, null)`. Изолированные тесты проверяют два диалога, замену DOM-узла, выход и несовпадение ID. Стили кандидата: `css/chat-unread-v2.css`, включая компактные мобильные размеры и `prefers-reduced-motion`.

**Не подключено в legacy HTML:** для rollout v2 потребуется создать контейнеры у карточек диалогов, подключить стили и вызвать presenter как onChange-клиент. До этого действующая лента и действующие счётчики остаются без изменений.


## Единый клиентский транспорт callable v2 (кандидат)

`ChatV2Transport` в `js/core/chat-v2-transport.js` объединяет пять явных операций: создание диалога, отправку сообщения, проверку статуса, индивидуальную квитанцию прочтения и сверку непрочитанных. Зависимость `invoke(endpoint, payload)` должна быть уже сконфигурирована вызывающей стороной для Firebase Functions `europe-west3`; адаптер сам не инициализирует Firebase, не хранит credentials и не подставляет `senderId`. Для реального SDK-адаптера `invoke` должен возвращать оригинальный результат `httpsCallable` в формате `{data}`.

Каждый вызов требует актуальный `getUserId()`; ответ не принимается после смены аккаунта или `invalidate()`. Входные ID/UUID проверяются до отправки, а серверные ответы — на точные типы, обязательные поля и совпадение `chatId/messageId`. Неизвестный статус, текст вместо числа или потерянная квитанция не становятся успешным подтверждением. Добавлены unit-тесты для всех пяти маршрутов, логина, некорректных ответов и поздних результатов.

**Это ещё не deployment и не UI rollout:** клиентское приложение пока не создаёт этот адаптер, не связывает его с `ChatDeliveryController`, `ChatReadVisibilityTracker` и `ChatUnreadController`, а серверные функции v2 не развёрнуты. Следующий этап — отдельная кандидатная orchestration-связка и интеграционная репетиция, затем аудит миграции и защищённое включение.


## Кандидатная интеграционная репетиция двух участников (без запуска)

`ChatV2Session` в `js/core/chat-v2-session.js` композиционно связывает `ChatV2Transport`, `ChatDeliveryController`, `ChatUnreadController` и `ChatReadVisibilityTracker`. Создание требует авторизованного пользователя и переданного `invoke` для `httpsCallable` из `europe-west3`; сессия не инициализирует Firebase и не меняет текущие маршруты приложения. Доступные операции: `createChat`, `prepare`, `send`, `reconcile`, `refreshRead`, `refreshUnread`, `watchIncoming` и `dispose`.

Прочтение входящего сообщения инициирует только `watchIncoming` после проверки видимости DOM, активности выбранного диалога и авторизованной сессии; каждый серверный receipt затем инициирует авторитетную сверку unread. Подтверждение отправителю приходит исключительно через отдельную проверку статуса сообщения. Никакой локальный таймер не формирует квитанции. При `dispose()` транспорт инвалидируется, наблюдатели DOM останавливаются, очереди и счётчики очищаются.

`tests/chat-v2-session.test.js` проверяет полный сценарий двух виртуальных пользователей: создание диалога → отправка → один непрочитанный → видимость меньше 75% без receipt → видимость 100% → receipt и unread=0 → подтверждённый статус read у отправителя. Отдельные проверки покрывают скрытую/неактивную вкладку, выход в момент запроса и смену аккаунта. Это репетиция на подменённом сервере, **не** реальный Firebase emulator end-to-end и **не** production rollout.

Следующие обязательные шаги: испытать цепочку на Firebase Emulator с утверждёнными правилами и индексами; подготовить реальные v2-разметку и управление жизненным циклом UI за выключенным feature flag; перед включением проверить аудит и план безопасной миграции старых чатов.
